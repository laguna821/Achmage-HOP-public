# Achmage Kordoc engine adapter

This package calls the installed **kordoc 4.21.31 public APIs** (`markdownToHwpx`, `validateHwpx`, `renderDocument`). Published npm gitHead: `f4e95b069d4f916365e5a13b5e6fc7b23f3f5c7c`, MIT; dist integrity `sha512-xtoznlbsQNbW4tsCXDLzhxRIBJNCROUSa/RDu8tL3Bzdju1YXAmgIaRXr/0I7ihTpjbnc1MT0OGZSxyFr7hRWg==`. The separately audited reference checkout is `1b860e9a606f4ce04f948092b174d998ce256bdc`; these two identifiers are not claimed to be identical. Dependencies and integrity hashes are fixed by `pnpm-lock.yaml`; install with `pnpm install --ignore-workspace --ignore-scripts --no-optional`. Optional OCR, raster/PDF runtimes, browser drivers and downloaded models are not installed. This is a bounded application adapter, not a claim that every Kordoc capability is exposed or validated.

Run `node worker.mjs --once` for a single NDJSON request; without the flag, requests are processed sequentially. Every request ends with a newline. There are no filename, shell command, account, URL-fetch or arbitrary engine-option inputs. The native bridge supplies the trusted Node executable/worker path; the app's windows use the WebView worker below and fall back to this Node worker only when that worker cannot start. The worker does not open or overwrite the active HOP document. The UI decides explicitly whether to open the generated bytes as a new document.

## WebView worker

The app's windows run the same engine in a Web Worker instead of a Node process. `web-worker.mjs` takes the same request lines and returns the same response lines as `worker.mjs` (`respond.mjs` is the protocol both share), carried by `postMessage` as `{seq,line}`. `scripts/achmage/prepare-kordoc-runtime.mjs` bundles it from the same audited closure for the browser into `kordoc-web/engine-worker.js`, which the studio build serves as `kordoc/engine-worker.js`.

The Node built-ins the closure imports are replaced by the files in `web/`:

- `Buffer`: the `buffer` 6.0.3 package (with `base64-js` and `ieee754`), installed as a global before any engine module runs (`web/globals.mjs`); `process` is a small stand-in (`web/process.mjs`).
- `crypto.createHash` (sha1, sha256): `@noble/hashes` 2.4.0.
- `zlib.inflateSync` / `inflateRawSync`: pako 1.0.11's zlib port, keeping Node's `maxOutputLength` stop, the truncated-stream error and the handling of bytes after the stream.
- `events`: an EventEmitter adapted from Node.js `lib/events.js` (MIT), with Node's listener order and error behaviour, for readable-stream 2. JSZip and readable-stream are pinned to the builds the Node bundle uses: JSZip's browser field would swap in its prebuilt dist, which has no `nodeStream`, and Kordoc reads ZIP entries through `nodeStream`.
- `fs`, `fs/promises`, `module`, `path`, `url`, `os`, `child_process`, `stream`, `util`: the engine's requests reach only `existsSync` and `readFile`, which miss like a missing file. Every other import serves code the engine's requests never reach (PDF reading, document writing, the CLI), and calling it fails instead of doing something else.

Both bundles (Node and WebView) leave out Kordoc's decryption of password-protected and distribution-restricted documents (HWP 5, HWP 3 and HWPX): packaging replaces those functions with ones that refuse, so the code they used drops out of the bundles, and it fails if either bundle still contains it. The engine reads only the HWPX documents it generates.

`test/web-shims.test.mjs` compares the replacements with the Node modules. Packaging runs the built worker with Node's `Buffer`, `process` and `global` removed (`scripts/achmage/kordoc-web-check.mjs`), so the worker must bring its own. It then requires the capabilities, generate, validate and render response lines to equal the Node worker's, character for character, for one fixed test document. This check runs the bundle in Node, not inside a WebView.

Requests:

```json
{"id":"unique-id","op":"generate","template":{"schemaVersion":1,"id":"...","name":"...","category":"personal","provenance":"personal","description":"...","roles":{},"layout":{}},"markdown":"# Title\n\n## Topic\n\nBody"}
```

The template uses the Studio `DocumentTemplate` contract. All five role objects are required. Other operations: `{id,op:"render",hwpxBase64}`, `{id,op:"validate",hwpxBase64}`, `{id,op:"capabilities"}`. No additional request properties are accepted. Responses are `{id,ok:true,result}` or `{id,ok:false,error:{code,message}}`. Errors do not contain stacks, process environment or raw document logs. Oversized requests are drained, and later frames can recover.

Generation result: `engine`, `hwpxBase64`, `sha256`, `pages:[{svg,width,height}]`, `warnings`, `validation`, `fontFamilies`, `fontFamiliesScope`. Pages are zero-based array entries in document order; dimensions are points. The SHA256 is of the exact final package that was validated and rendered. Studio independently verifies this hash. Display SVG as an image resource, never as HTML. All package writes occur in memory; no caller filesystem writes are exposed.

## Generation and composition

1. Validate bounded Markdown and the selected template. Tokenize source using Markdown-It and mark semantic roles in this **new generated document only**.
2. Call the pinned Kordoc generator with the selected official/report/plan/notice/minutes/gaejosik/press/ministry/bangchim preset, paper/orientation and public font/body options.
3. Without an agency, resolve each generated paragraph/cell marker; append cloned header styles with the selected role's font, size, bold, spacing, alignment and line spacing. Remove markers. Explicit role `bold:false` removes preset bold. Independently marked Markdown strong ranges remain bold; ambiguous multi-line strong is rejected rather than silently flattened. No existing document IDs are assumed or edited.
4. `report`/`plan` cover uses the actual upstream cover generator. Their TOC is a separate Achmage XML composition because upstream V5 does not emit a report/plan TOC. It contains heading labels and real paragraph page breaks, **without automatic page-number fields**. Cover requires `#` title, TOC requires subheadings. Unsupported preset/front-matter combinations fail explicitly.
5. Refresh preview text, discard line caches, keep `mimetype` first and uncompressed, normalize generated timestamps, validate the final HWPX, and render all pages using Kordoc reflow. Preview and import use these same bytes.

Currently supported role composition: headings, plain/inline Markdown paragraphs, lists and GFM tables (including empty cells). Code blocks, raw HTML and image inputs are explicit unsupported inputs; no network images are fetched. Existing HWPX byte rendering/validation does not claim full editing or preservation. Reflow/installed-font differences from HOP or Hancom remain possible, and engine warnings are retained.

Limits: request 16 MiB (Markdown has no separate limit), response 32 MiB, ZIP 8 MiB, expanded ZIP 32 MiB, 2,048 entries, 1,920² block role marks (two code points each, so every table cell of a long document fits), 1,024 bold spans, SVG previews of the first 100 pages (the whole document is generated and `pageCount` reports it). ZIP traversal, duplicate central-directory names, unsupported encryption/ZIP64 and executable/external SVG references are rejected. Native process timeout/cancellation is owned by the IPC wrapper.

No paid model call, Hancom 한글 application, or running native app is used. HanMark 2.7.0 source inspected at commit `3db078d75851ae8d94dcc96eff45a6fad1102d63`: `src/io/kordocEngine.ts` generates, applies a document-style stage, validates, then previews; `src/ui/QuickHwpxPreviewView.ts` uses versioned/cache-keyed generated preview and exports the corresponding configured document. `HwpxTemplateManagerModal.ts` manages library choices rather than proving every template page; Obsidian settings/workspace APIs are not copied into this adapter. Its locked Kordoc 4.15.7 version is distinct from this adapter's 4.21.31. The current role and TOC composition code is new application code, not an attribution-free copy of HanMark implementation.

## Actual agency and preset catalog

The capabilities response obtains all 52 agency names plus 공통 through the installed public agencyNames/agencyStyle APIs. presets contains all nine names; coverPresets/tocPresets/coverTocPresets contain report, plan, gaejosik, ministry, bangchim. For the latter three, cover and TOC are the real upstream composition. Notice silently ignored front-matter options in a direct upstream probe, so this adapter explicitly rejects that combination. Automatic TOC page-number fields remain unsupported.

layout.agency selects an exact catalog name. It is accepted only for report, plan, ministry, gaejosik and press; other combinations and unknown names fail. Agency selection preserves upstream font/size/paragraph/table/band defaults: the five app roles do not silently overwrite them. Optional layout.agencyRoleOverrides is a unique array drawn from title/heading/body/tableHeader/tableCell; only these explicit roles use the existing full role override stage. Overrides without an agency are rejected. Explicit Markdown strong is still preserved independently.

agencies entries expose name, reportAvailable, pressAvailable, reportUsesCommonFallback, the actual style {report,press,band}, fontFamilies, fontFamiliesByPreset and fontFamiliesScope. The font lists here are declarations including common fallback, not proof of every font used by preset decorations. Ten agencies have no report rule and generate with the upstream common rule and an explicit warning. These extracted patterns are not official acceptance certification and cannot be losslessly represented as the app's five generic roles. Existing-document agency style editing is outside this new-document generation contract.

Every generated/rendered result also exposes fontFamilies collected from all seven language font references of charPr IDs actually used by runs in all section XMLs. This intentionally includes references for language slots not necessarily present in visible text; it is not a per-character font-fallback prediction. It avoids treating every unused font-table entry as a required font. The parent app can inspect this final list before opening the result.

Validation: 22 Node tests, including 53 catalogs × press/report = 106 actual generated HWPX/SVG outputs, exact body font lookup, missing-report fallback, nine presets, three additional native front-matter combinations, five agency-enabled generator families, selective overrides, all old framing/bounds/bold tests. Six Studio tests exercise actual worker results/capabilities, hash/font metadata rejection and the unchanged bounded queue. No vendor app or paid inference is executed by these tests.
